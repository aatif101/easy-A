# Phase 3.5: Ranking Search Performance at Full Coverage - Context

**Gathered:** 2026-09-20
**Status:** Ready for planning
**Source:** Captured directly from the user's phase specification (equivalent to discuss-phase output).

<domain>
## Phase Boundary

Make ranking search fast enough to serve **all ~3,782 Spring 2027 Tampa sections** over the hosted
Supabase database — search-page latency **well under ~1.5s p95** — **without changing the easiness
scoring model or the API response contract.**

This phase is *performance and data-scoping only*. It is carved out of the Phase 4 hosted beta
because REQ-PERF-01 is now a blocker. Deployment, CI, observability, and the operator runbook
remain in Phase 4 and are out of scope here. Grades and syllabi ingestion are untouched.

</domain>

<problem>
## Why This Phase Exists (confirmed root cause)

After the move to hosted Supabase and widened coverage, a 132-section pilot measured **~600 seconds**
for a single rankings search (local Postgres at 77 sections was ~10.1s — see REQ-PERF-01).

Root cause is confirmed in `src/easy_a/api/routes/rankings.py`:
- `search_rankings` (line ~49) calls `_rank_candidate_sections` (line ~90), which selects **every**
  candidate section in the term, then loops CRN-by-CRN calling `rank_section()`
  (`src/easy_a/rankings/service.py:31`).
- Each `rank_section()` fires several per-section queries (course, instructor, seats, attributes,
  analytics, signals).
- The endpoint ranks the **whole term on every request** and only sorts/paginates afterward.

This is an N+1 that was invisible on sub-ms local Postgres and explodes over remote Supabase (a
network round-trip per query per section).

</problem>

<decisions>
## Implementation Decisions

### Locked hard constraints (do not violate)
- **D-01 — Approach: precompute + read-through.** Precompute rankings into a derived/cached table
  (working name `section_rankings`), refreshed as part of / right after the refresh pipeline. The
  planner may refine mechanism but must hold this intent.
- **D-02 — Scoring model UNCHANGED.** The easiness scoring model is not rewritten. Cached values
  MUST be **byte-for-byte identical** to what the current on-demand `rank_section()`
  (`src/easy_a/rankings/service.py`) produces. No scoring rewrite, no re-derivation of numbers.
- **D-03 — API response contract identical.** `GET /api/v1/rankings/search` keeps the same response
  shape: `items` / `total` / `limit` / `offset`, and the same sort values (`easiness_desc`,
  `easiness_asc`, `withdrawal_asc`, `seats_desc`, `course`). Same filter surface
  (subject / course / gened / delivery / open-seats / min-easiness / confidence).
- **D-04 — Honest-data semantics preserved.** Unavailable stays unavailable; provenance /
  confidence / `effective_n` remain intact; no fabricated values. (This is the project's core
  value — every number is a real observed outcome with a visible denominator, source, and
  timestamp, or the product says it's unavailable.)
- **D-05 — No grades/syllabi changes; no secrets in git.**

### Search path rewrite
- **D-06 — Pagination and filtering IN SQL.** Rewrite the search path to read from the cached table
  with sort, filter, and pagination performed in SQL — cost O(one page), not O(whole term).
  Eliminate the per-section N+1 entirely.

### Migration
- **D-07 — Alembic migration chained after `0002_create_section_syllabus_tables`.** New migration
  under `migrations/versions/` (current head is `0002_create_section_syllabus_tables.py`) creates
  the derived table.

### Seat freshness relationship (decide + document)
- **D-08 — Cached ranking vs. live seat snapshot.** Seats can be fresher than the cached ranking.
  The planner/researcher must **decide and document** how the cached ranking row relates to the
  live "latest observed seats" snapshot, so that stale seats never corrupt scores AND
  seat-freshness / open-seats semantics stay correct in the response. (Open question for research —
  see below.)

### Cache freshness / staleness guard
- **D-09 — Refresh is documented and tested.** How and when `section_rankings` is (re)populated must
  be documented and covered by a test, so the cache cannot silently go stale after an ingestion.

### CHM 2045 vs CHM 2045L
- **D-10 — Course-number suffix / lab-section matching.** Fix the CHM 2045 vs CHM 2045L issue:
  course-number suffix (lab sections) must be matched/scoped correctly in **ingest** and in the
  **campus/target guard** so full-scale runs stay clean. (Related guard/refresh code lives in
  `src/easy_a/refresh/coverage.py` and `src/easy_a/refresh/cleanup.py`. STATE.md notes 33 base
  courses have suffix variants whose query behavior needs attention before scaling — do not weaken
  the exact-course guard.)

### Claude's Discretion
- Exact table schema and columns of the derived table (as long as parity + contract hold).
- Whether the cache is a real table, materialized view, or equivalent — provided D-07/D-08/D-09 are
  satisfied and it works on the PostgreSQL/Supabase integration path.
- Indexing strategy for the sort/filter columns.
- Test seeding mechanism for the larger performance dataset.

</decisions>

<acceptance>
## Acceptance / Verification (success criteria)

1. **Correctness parity (automated).** For a sample of sections and for full-course searches, the
   cached-table results match the current on-demand rankings **exactly** — same order, same scores,
   same fields. Ship an automated parity test.
2. **Performance (measured, real numbers).** Measure a rankings search against Supabase **before and
   after**, at the current pilot size AND against a **larger seeded set** (seed/populate more
   sections in a test if needed). After: search page **< ~1.5s p95**. Report dataset size and
   environment with every number.
3. **Quality unchanged.** `scripts/check_data_quality.py` still reports **0 errors**; Tampa-only
   guard clean.
4. **Cache freshness tested.** Document + test how/when `section_rankings` is refreshed so it cannot
   silently go stale after an ingestion.
5. **Full test suite green**, including the PostgreSQL integration path
   (`EASY_A_TEST_POSTGRES_URL`).

</acceptance>

<open_questions>
## Open Questions for Research

1. **Seat freshness vs. cached ranking (D-08).** Does `rank_section()` incorporate live seat data
   into the score, or only into displayed seat/freshness fields? Determine whether seats affect the
   cached score at all — this decides whether the response must join live seat snapshots on top of
   the cached ranking row, and how "open-seats" filtering/sorting stays correct without re-ranking.
2. **Cache population point.** Where in the refresh pipeline (`coverage.py` / `service.py`) to
   populate/refresh `section_rankings` so it's atomic with an ingestion and can't go stale (D-09).
3. **Derived-table mechanism.** Real table vs. materialized view under Supabase/Postgres, and which
   works cleanly with Alembic and the existing test harness.
4. **Parity harness.** Best way to assert byte-for-byte equality between on-demand `rank_section()`
   and the cached row across all fields (scores, provenance, confidence, effective_n).
5. **CHM 2045L suffix behavior (D-10).** Exact query mechanics of USF's course lookup that pull in
   `L`-suffixed lab sections, and where the exact-course guard must scope by full course number —
   in ingest and in the target/campus guard — without weakening the guard.
6. **Performance measurement + seeding.** How to seed a realistic larger dataset (toward ~3,782
   sections) for a repeatable p95 measurement against Supabase.

</open_questions>
