**Sort-key logic to port into SQL `ORDER BY`** (`api/routes/rankings.py:148-162`,
`_ranking_sort_key` — the Python version to translate, including the NULL-seats pitfall):
```python
def _ranking_sort_key(ranking: SectionRanking, sort: RankingSort) -> tuple[float | str, ...]:
    course_tiebreak = (ranking.subject, ranking.course_number, ranking.crn)
    if sort is RankingSort.easiness_asc:
        return (ranking.easiness_score, *course_tiebreak)
    if sort is RankingSort.withdrawal_asc:
        return (ranking.smoothed_withdrawal_rate, *course_tiebreak)
    if sort is RankingSort.seats_desc:
        seats_remaining = ranking.seats_remaining if ranking.seats_remaining is not None else -1
        return (-float(seats_remaining), *course_tiebreak)
    if sort is RankingSort.course:
        return course_tiebreak
    return (-ranking.easiness_score, *course_tiebreak)
```
**PITFALL (from RESEARCH.md, verified against this exact code):** the `seats_desc` branch
normalizes `None` → `-1` in Python before comparing. The SQL replacement MUST use
`func.coalesce(live_seats_remaining, -1).desc()` — never rely on either engine's default NULL
ordering (SQLite sorts NULL first; Postgres differs by ASC/DESC), or SQLite unit tests and the
Postgres integration test will silently disagree on result order.

**Live seat 3-tier fallback to reproduce exactly** (`src/easy_a/rankings/service.py:210-269`,
`_seat_info_for` — the function whose *logic*, not literal SQLAlchemy ORM calls, the rewritten SQL
join must reproduce):
```python
def _seat_info_for(session: Session, *, section: Section, term_code: str) -> SeatInfo:
    latest_snapshot = (
        session.execute(
            select(SeatSnapshot)
            .where(SeatSnapshot.section_id == section.id)
            .order_by(SeatSnapshot.observed_at.desc(), SeatSnapshot.id.desc())
            .limit(1)
        )
        .scalars()
        .first()
    )
    if latest_snapshot is not None:
        return SeatInfo(**snapshot_freshness(latest_snapshot).model_dump(), capacity=latest_snapshot.capacity, ...)
    if any(value is not None for value in (section.capacity, section.enrollment, section.seats_remaining, section.wait_seats_available)):
        return SeatInfo(capacity=section.capacity, ...)  # tier 2: section's own current columns
    return SeatInfo(capacity=None, ...)  # tier 3: unavailable
```
Tier 1 = latest `SeatSnapshot` ordered by `(observed_at DESC, id DESC)` (deterministic tie-break —
see the same pattern already exercised in `tests/refresh/test_postgres_coverage.py:53` comment
"Equal timestamps use the snapshot id as a deterministic tie-breaker"). Tier 2 = `sections`' own
current seat columns if any is non-NULL. Tier 3 = all-NULL, `unavailable` provenance. All three tiers
must be reachable from the rewritten SQL/join, not just tier 1, or a section with stale/no snapshot
but populated `sections.seats_remaining` will silently show "unavailable" in search while
`GET /api/v1/rankings/section` for the same CRN shows real numbers.

**Freshness recomputation — never cache these fields** (`src/easy_a/schedule/freshness.py:25-68`,
full file read): `classify_observation()` defaults `as_of=datetime.now(UTC)` (line 40) — call this
function at request time against the live-joined `observed_at`, never store its output in
`section_rankings`.

**Total/pagination shared-predicate pitfall (from RESEARCH.md, Pitfall 4):** build one SQLAlchemy
`Select` with every filter (including the live seat join and `seats_open`) applied, then derive both
`items` (`.order_by(...).limit(...).offset(...)`) and `total`
(`select(func.count()).select_from(<same filtered subquery>)`) from that single statement object —
do not write the `COUNT` query independently, or a filter added to one and forgotten in the other
will make `total` disagree with the number of `items` a client sees across all pages. The current
code's implicit correctness here (`total = len(rankings)` computed from the same Python list just
filtered, `api/routes/rankings.py:81`) is exactly the invariant the SQL rewrite must preserve
structurally.

**`_dependent_ids` helper — generic over model, already accepts new types via its type union**
(`cleanup.py:486-495`):
```python
def _dependent_ids(
    session: Session,
    model: type[SeatSnapshot] | type[SectionInstructor] | type[Syllabus],
    section_ids: frozenset[int],
) -> frozenset[int]:
    if not section_ids:
        return frozenset()
    return frozenset(
        session.scalars(select(model.id).where(model.section_id.in_(section_ids))).all()
    )
```
Widen the type union to include `SectionRankingCache`.

(`cleanup.py:455-483` and `515-554`): add a `section_ranking_ids` field to `_IdentitySnapshot`
(populated the same way as `seat_snapshot_ids = frozenset(session.scalars(select(SeatSnapshot.id)))`

`_verify_identities` (lines 524-545) so a stale-cache regression fails the same identity check that
already guards `SeatSnapshot`/`SectionInstructor`/`Syllabus`.

**Why this matters (from RESEARCH.md Pitfall 2, restated for the planner):** if
`section_rankings.section_id` has `ondelete="CASCADE"` but `cleanup.py` doesn't also do its own
explicit delete + identity check, a DB-level cascade alone would silently succeed while leaving no
audit trail — `cleanup.py` deliberately does its own explicit, verified deletes for exactly this kind
of dependent-data safety; don't rely on the FK cascade as the only mechanism.
