<objective>
Turn the inherited UI contract into a traceable state and payload matrix, confirm every requirement
has an owning phase, and register every external dependency with an owner and the phase it blocks.

Purpose: ROADMAP Phase 1 success criterion 5, and the REQ-UI-01 component and state contract and
REQ-OPS-01 source and provisioning planning that Phase 1 establishes for later phases. The UI
direction and the five surfaces already exist in `01-UI-SPEC.md`; what does not exist is a row per
state naming the field that expresses it and the phase that owns it.
Output: `01-UI-API-STATE-CONTRACT.md` and `01-DEPENDENCY-REGISTER.md`.

Everything here is a specification. Nothing in this plan renders, implements or verifies a screen.
</objective>

    Write 01-UI-API-STATE-CONTRACT.md as two matrices plus a short preamble stating that this
    document specifies and does not implement.

    First matrix, the surfaces. One section per surface beginning `### Surface: `, five in total —
    search and results, linkable section detail, methodology and data coverage, watch signup and
    confirmation, and private watch management. Each section states the arrangement and interaction
    obligations, the payload obligations as named fields rather than prose, the implementing phase
    and the verifying phase. Include the search state persistence obligation — term, query, filters,
    sort and page live in the URL and restoration includes result position — and the section detail
    route identity of term plus CRN. Include the ordering rules: default ordering by grade ease
    descending, unscored rows after scored rows with no rank number, nulls last in both numeric
    directions, and that an evidence join must never remove a section.

    Second matrix, the states. One table row per state, each carrying a stable identifier of the
    form `ST-NN` in its first column, then the state name, the named payload field or reason that
    expresses it, the user-facing copy taken from the UI spec's copywriting contract, the surfaces
    it appears on, the implementing phase and the verifying phase. Cover at minimum the thirteen
    states the roadmap's Phase 6 criterion enumerates: no history, small sample, no measured
    reference, withdrawal-only, suppressed or invalid source, no professor match, no current
    syllabus, missing profile verification, full and over capacity, stale seats, unknown or
    cancelled, API outage, and empty or unsupported-term search. Add rows for any further state the
    UI spec's considerations table names.

    Then add a section mapping the eight UI consideration categories, each with a stable identifier
    of the form `UIC-NN` in its first column: empty, loading, error, populated, partial, overflow,
    zero-one-many and long-text. Each row states which state identifiers and which surfaces carry
    that category's obligations, so a later phase can check a category is represented rather than
    re-reading prose. Do not weaken any of the eight resolutions inherited from the UI spec.

    Add a short accessibility and acceptance section restating the obligations as specification: the
    three target widths and double zoom, keyboard-only navigation with persistent visible focus,
    focus containment and restoration for drawers and dialogs, a text alternative for every chart,
    readable chip contrast, status conveyed by text and not by colour alone, and the minimum
    interactive hit area. Record that browser evidence for these belongs to Phase 6 and that a
    mockup, a generated image, a fixture-only page or a passing component test does not satisfy them.

    Add a removals section naming the two production fabrication risks with their owning phase: the
    implicit fixture fallback and the hard-coded term preference in the frontend API module. Per
    D-02 the supported term is expressed through configuration and contract, not a frontend
    constant.

    Cite the five metric states from the method contract by name and link to that document as their
    definition. Do not redefine them here.
  </action>
