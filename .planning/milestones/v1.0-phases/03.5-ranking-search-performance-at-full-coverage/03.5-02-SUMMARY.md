## Decisions Made

- Used the same window-function latest-snapshot query on SQLite and PostgreSQL, including snapshot ID as the deterministic timestamp tie-break.
- Derived count and items from the same filtered statement so filter changes cannot drift between totals and pages.
- Used a correlated `EXISTS` containing the live Course-to-CourseAttribute join for GenEd filtering, preventing duplicate source attributes from duplicating rankings.
- Kept REQ-PERF-01 open because hosted full-coverage p95 acceptance belongs to Plan 03.5-05.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Made joined missing-snapshot state explicit during cache hydration**
- **Found during:** Task 1 GREEN
- **Issue:** Plan 01's `hydrate_ranking(..., seat_snapshot=None)` interpreted `None` as “not loaded” and performed a seat query, making a query-free joined fallback impossible.
- **Fix:** Added a private omitted-argument sentinel; callers that omit the argument retain the old lookup behavior, while the search route passes explicit `None` for a known missing snapshot.
- **Files modified:** `src/easy_a/rankings/cache.py`
- **Verification:** The search-query counter proves exactly two SELECTs for a two-row page containing snapshot and no-snapshot rows.
- **Committed in:** `b9ff0d3`

**2. [Rule 3 - Blocking] Populated the derived cache in legacy API fixtures**
- **Found during:** Existing API contract verification
- **Issue:** Existing search tests seeded canonical sections and grades but no derived cache rows, so a correct cache-only route returned an empty result.
- **Fix:** Refreshed the cache at the end of the shared search-data seeder; production remains cache-only and does not rebuild data during GET requests.
- **Files modified:** `tests/api/test_rankings_api.py`
- **Verification:** All 17 unaffected existing ranking API tests pass; the sole remaining API-file failure is the known user-owned ten-target configuration mismatch.
- **Committed in:** `b9ff0d3`

**3. [Rule 1 - Bug] Prevented duplicate GenEd source rows from duplicating rankings**
- **Found during:** Task 2 review
- **Issue:** A direct live attribute join could repeat one ranking and inflate `total` when source data contained duplicate attribute codes.
- **Fix:** Kept the live Course-to-CourseAttribute join inside a correlated parameterized `EXISTS` predicate.
- **Files modified:** `src/easy_a/api/routes/rankings.py`, `tests/api/test_rankings_search_sql.py`
- **Verification:** Duplicate SMEL source rows still return exactly two distinct MAC rankings and a total of two.
- **Committed in:** `fe874ae`

**Total deviations:** 3 auto-fixed (1 bug, 2 blocking issues)
**Impact on plan:** The changes close query-count and fixture prerequisites required to preserve the stated cache-only search and contract guarantees.
