### Locked Decisions

- **D-01 — Approach: precompute + read-through.** Precompute rankings into a derived/cached table
  (working name `section_rankings`), refreshed as part of / right after the refresh pipeline. The
  planner may refine mechanism but must hold this intent.
- **D-02 — Scoring model UNCHANGED.** The easiness scoring model is not rewritten. Cached values
  MUST be **byte-for-byte identical** to what the current on-demand `rank_section()`
  (`src/easy_a/rankings/service.py`) produces. No scoring rewrite, no re-derivation of numbers.
- **D-03 — API response contract identical.** `GET /api/v1/rankings/search` keeps the same response
  shape: `items` / `total` / `limit` / `offset`, and the same sort values (`easiness_desc`,
  `easiness_asc`, `withdrawal_asc`, `seats_desc`, `course`). Same filter surface
  (subject / course / gened / delivery / open-seats / min-easiness / confidence).
- **D-04 — Honest-data semantics preserved.** Unavailable stays unavailable; provenance /
  confidence / `effective_n` remain intact; no fabricated values.
- **D-05 — No grades/syllabi changes; no secrets in git.**
- **D-06 — Pagination and filtering IN SQL.** Rewrite the search path to read from the cached table
  with sort, filter, and pagination performed in SQL — cost O(one page), not O(whole term).
  Eliminate the per-section N+1 entirely.
- **D-07 — Alembic migration chained after `0002_create_section_syllabus_tables`.** New migration
  under `migrations/versions/` (current head is `0002_create_section_syllabus_tables.py`) creates
  the derived table.
- **D-08 — Cached ranking vs. live seat snapshot.** Seats can be fresher than the cached ranking.
  The planner/researcher must decide and document how the cached ranking row relates to the live
  "latest observed seats" snapshot, so that stale seats never corrupt scores AND seat-freshness /
  open-seats semantics stay correct in the response. (Resolved below — see "Key Research Findings".)
- **D-09 — Refresh is documented and tested.** How and when `section_rankings` is (re)populated must
  be documented and covered by a test, so the cache cannot silently go stale after an ingestion.
- **D-10 — Course-number suffix / lab-section matching.** Fix the CHM 2045 vs CHM 2045L issue:
  course-number suffix (lab sections) must be matched/scoped correctly in ingest and in the
  campus/target guard so full-scale runs stay clean. Do not weaken the exact-course guard.

## Summary

The 600s-per-search regression is real and precisely located: `search_rankings` →
`_rank_candidate_sections` (`src/easy_a/api/routes/rankings.py:90-131`) selects every CRN in the
term and calls `rank_section()` (`src/easy_a/rankings/service.py:31`) once per CRN, and each
`rank_section()` call independently re-fires the *entire* course-level grade-aggregation pipeline
(`get_current_section_historical_analytics` in `src/easy_a/analytics/queries.py:135-194`, itself
composed of course/subject/global grade-aggregate queries) plus per-section instructor, seat,
gened, and signal-resolution queries. Over a local sub-millisecond Postgres this was invisible;
over hosted Supabase, at ~10-15 round trips per section, it becomes O(sections × queries) real
network round trips — the observed 600.61s for 132 sections is consistent with that model.

Two structural facts, verified by reading the code, resolve the phase's central open question
(D-08): **`rank_section()`'s score fields (`easiness_score`, `smoothed_withdrawal_rate`,
`confidence_label`, `effective_n`, `score_source`, and everything inside
`historical_analytics`) are computed entirely from `GradeDistribution`/`Term`/`Section` joins with
zero reference to seats anywhere in the call graph** (`src/easy_a/analytics/queries.py`,
`src/easy_a/analytics/scoring.py`). Seats only ever reach the `SeatInfo` sub-object and the
top-level `seats_remaining` mirror field, and that seat data is itself **time-relative** —
`snapshot_freshness()`/`classify_observation()` call `datetime.now(UTC)` by default
(`src/easy_a/schedule/freshness.py:25-51`) to compute `freshness`/`age_seconds` at the instant of
the request. This means the cached table can safely store every score/analytics/provenance field
byte-for-byte, but **must not** cache `seats.observed_at` / `freshness` / `age_seconds` /
`seats_remaining` / `capacity` / `enrollment` / `wait_seats_available` as static values — those
must be joined live from `seat_snapshots` (with the exact two-tier fallback `rank_section` already
uses) at read time, on every request, computed against "now."

The second load-bearing fact: `quality/checks.py:_check_analytics` (lines ~417-452) already proves
the fix pattern the precompute job should follow — it groups candidate sections by
`(subject, course_number)` and calls `get_current_section_historical_analytics` **once per course**,
not once per CRN, because that function itself returns *every* section's stats for the course in
one call. `rank_section()` (and therefore today's `_rank_candidate_sections` and
`rank_course_sections`) throws away all but one row every time, which means a naive "just call
`rank_section()` once per CRN inside the refresh job" fix would still be O(sections-in-course²)
work and would remain too slow to run against remote Supabase at ~3,782 sections. The
population job must batch by course exactly like the quality checker does, while reusing
`rank_section`'s private per-section composition helpers verbatim to guarantee byte-for-byte parity.

Also verified directly: the CHM 2045 / CHM 2045L failure is not a weak guard — it is a *correct,
overly blunt* guard. `refresh_targets` (`src/easy_a/refresh/coverage.py:138-151`) fires a schedule
search with `P_NUM = course.number` (`src/easy_a/schedule/client.py:77`), which USF's staff
schedule search resolves as a prefix/substring match, returning both `CHM 2045` and `CHM 2045L`
rows. The guard then raises `ValueError` if **any** returned row's `(subject, course_number)` pair
doesn't exactly match the target, aborting the whole transaction — correct for safety, but it
throws away the valid `CHM 2045` rows along with the `CHM 2045L` rows. The fix is a **pre-filter**,
not a guard weakening: drop rows whose `(subject, course_number)` isn't an exact match *before*
applying the (unchanged, still-strict) Tampa-campus and CRN-scope checks to the remaining rows.

Finally, on mechanism (Claude's Discretion + open question #3): a **real table**, not a
materialized view, is the only option consistent with this repo's existing test architecture. The
default unit-test path (`tests/conftest.py`, `tests/api/test_rankings_api.py`) builds schema via
`Base.metadata.create_all(engine)` on **in-memory SQLite**, and the PostgreSQL integration test
(`tests/refresh/test_postgres_coverage.py`) does the same via `Base.metadata.create_all(connection)`
against a fresh Postgres schema — **neither path runs Alembic migrations**, and SQLite has no
materialized-view concept at all. A materialized view would be invisible to the 192-test SQLite
default suite and would require special-casing the Postgres integration test. A plain
SQLAlchemy-mapped table, refreshed with ordinary `INSERT`/`UPDATE` inside the refresh pipeline's
existing `factory.begin()` transactions, works identically across SQLite and Postgres, is picked up
automatically by `Base.metadata.create_all()`, and needs no `REFRESH MATERIALIZED VIEW CONCURRENTLY`
unique-index machinery.

**Primary recommendation:** Add a real table `section_rankings` (SQLAlchemy model with a distinct
Python class name — see pitfalls), an Alembic migration chained after `0002_...`, and a
refresh-pipeline step that batches score computation by `(subject, course_number)` (mirroring
`_check_analytics`) and reuses `rank_section`'s private composition helpers to build each row —
excluding the seat-display fields, which the rewritten `search_rankings` route joins live from
`seat_snapshots`/`sections` at request time using the same fallback tiers `rank_section` uses
today. Move all sort/filter/pagination into SQL against this table.

## Architectural Responsibility Map

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| Easiness score computation (grade aggregation, Bayesian shrinkage, confidence) | Refresh pipeline (batch job) | API/Backend (read-only, cached) | D-02 forbids re-deriving scores at request time; computing once per ingestion and storing is the only way to hit sub-1.5s while keeping the exact same math. |
| Search sort/filter/pagination | Database / Storage (SQL) | API/Backend (query construction) | D-06 requires SQL-side sort/filter/pagination; the API layer's job becomes "build the right WHERE/ORDER BY/LIMIT," not "loop and compute." |
| Live seat freshness / open-seats display | API/Backend (per-request join) | Database / Storage (SeatSnapshot table, unchanged) | Seats are observed independently of the score (verified — no code path threads seat data into scoring) and are explicitly allowed to be fresher than the cached ranking (D-08); must be joined at read time, not cached. |
| Cache population / invalidation | Refresh pipeline (`refresh/coverage.py`, `refresh/service.py`) | Database / Storage (derived table + FK cascade) | D-01/D-09 require population to be part of/right after refresh, atomic with ingestion, and never silently stale. |
| Course-number suffix / lab-section scoping | Refresh pipeline ingest (`schedule/client.py` query construction, `refresh/coverage.py` guard) | — | The mismatch originates in the upstream USF search behavior (substring match on `P_NUM`), not in the database layer; the fix belongs where the schedule response is filtered, before ingest. |
| Campus-contamination cleanup (existing, PR #18) | Refresh pipeline (`refresh/cleanup.py`) | Database / Storage | Unrelated to D-10's suffix issue (campus vs. course-number are different guards) but the *cleanup* tool must be extended to also purge `section_rankings` rows for any section it deletes — see pitfalls. |

## Key Research Findings (Open Questions Resolved)

### 1. Does `rank_section()` incorporate live seat data into the score? (D-08)

**No — verified by reading the full call graph this session.**

`rank_section()` (`src/easy_a/rankings/service.py:31-98`) builds the score exclusively from
`analytics_stats = self._historical_stats_for_section(...)` (lines 53-59), which calls
`get_current_section_historical_analytics` (`src/easy_a/analytics/queries.py:135-194`). That
function's entire data source is `GradeDistribution` joined to `Term`/`Section`
(`_fetch_course_grade_observations`, `_fetch_instructor_course_grade_observations`,
`src/easy_a/analytics/queries.py:274-354`) — there is no `SeatSnapshot`, `Section.seats_remaining`,
or `Section.capacity` reference anywhere in `analytics/queries.py` or `analytics/scoring.py`.
Seats enter `SectionRanking` only through the separate `seats = self._seat_info_for(...)` call
(`service.py:51`), which populates the `seats: SeatInfo` sub-object and the top-level
`seats_remaining` mirror field (`service.py:80-81`) — a completely independent code path from the
score.

Furthermore, `SeatInfo`'s `freshness`/`age_seconds` fields (`src/easy_a/rankings/models.py:42-52`)
are populated by `snapshot_freshness()` → `classify_observation()`
(`src/easy_a/schedule/freshness.py:25-68`), which default `as_of` to `datetime.now(UTC)`
(`freshness.py:40`) when not explicitly supplied. **These fields are wall-clock-relative and
recomputed on every call** — they are not stable data that can be cached and replayed later without
becoming stale/wrong the moment time passes.

**Design consequence:** the `section_rankings` cache table stores every score/analytics/provenance
field verbatim (safe — those are deterministic given DB state, confirmed no `datetime.now()`
anywhere in `analytics/scoring.py`, `analytics/grades.py`, or `signals/resolver.py`), but excludes
`seats.observed_at`, `seats.freshness`, `seats.age_seconds`, `seats.capacity`, `seats.enrollment`,
`seats.seats_remaining`, `seats.wait_seats_available`, and the top-level `seats_remaining` mirror.
The rewritten search route must LEFT JOIN the latest `seat_snapshots` row per section (or fall back
to the section's own current seat columns, or `None` — see the exact three-tier fallback quoted
under "Common Pitfalls") and recompute freshness/age at request time using the existing
`snapshot_freshness()` function, exactly as `GET /api/v1/rankings/section` does today. This keeps
"seats can be fresher than the cached ranking" true by construction and keeps `seats_open`
filtering/`seats_desc` sorting correct without re-ranking (D-08 satisfied: score and seat freshness
are two independently-refreshed data sources joined at read time).

### 2. Where to populate/refresh `section_rankings` (D-09)

`refresh_data()` (`src/easy_a/refresh/service.py:40-128`) already runs term-setup → catalog →
schedule → grades → syllabi as independently committed stages (`_run_stage`, each wrapped in its
own `factory.begin()` transaction), then computes a final `RefreshResult` summary by re-querying
counts in a fresh session (lines 87-111). The natural, minimal-blast-radius hook is a **new final
stage** — `_refresh_rankings_cache` — added after the syllabi stage and before the summary block,
so it runs whenever `refresh_data()` is invoked (`scripts/refresh_data.py`), using the same
`RefreshStageError` wrapping so a failure is reported like any other stage failure and does not
silently succeed.

`refresh_targets()` (`src/easy_a/refresh/coverage.py:72-164`, driving `scripts/refresh_course_coverage.py`
and `scripts/refresh_seats.py` with `coverage=True`/`False`) is the **other** ingestion entry point
actually exercised by the pilot (STATE.md's 132-section pilot ran through this path, not through
`refresh_data()`). Because both entry points can mutate `sections`/`grade_distributions` and both
are used in practice, the population step should be a **standalone function** —
e.g. `refresh_section_rankings(session, *, term)` in a new `src/easy_a/rankings/cache.py` — called
from *both* `refresh_targets()` (per-target, after a successful schedule ingest) and
`refresh_data()`'s new stage, rather than duplicating logic in each. Being importable and callable
means the parity/freshness tests (D-09's "covered by a test" requirement) can invoke it directly
against a seeded session without needing to run either whole pipeline.

**Atomicity:** because `refresh_targets()` already ingests per-target inside the caller's own
transaction ("Caller owns transaction; failures must roll it back" — `coverage.py:85` docstring),
calling `refresh_section_rankings()` for the just-ingested target's course **inside that same
transaction**, right after `ingest_schedule_html` returns, makes cache population atomic with
ingestion by construction — a crash or validation failure before commit rolls back the schedule
ingest *and* the cache write together, so the two can never observably diverge. This is the
simplest way to satisfy "can't go stale after an ingestion" without inventing a separate
job-queue/staleness-detection mechanism.

### 3. Real table vs. materialized view (open question #3)

**Real table — settled by the existing test architecture, not by preference.** `tests/conftest.py`
and `tests/api/test_rankings_api.py` both build schema with
`Base.metadata.create_all(engine)`/`(connection)` against **SQLite** for the default (no-Postgres)
suite; `tests/refresh/test_postgres_coverage.py` does the identical thing against a **fresh Postgres
schema**, and explicitly does **not** run Alembic (`Base.metadata.create_all(connection)`,
line 31 — no `alembic upgrade` call anywhere in that test). SQLite has no materialized-view
support at all, so a materialized view would be entirely absent from 192+ of the current tests and
would require a parallel plain-table shadow definition just to keep the SQLite suite passing —
duplicating the schema rather than sharing one definition. A plain `Base`-mapped ORM class avoids
this fork entirely: one model definition serves `create_all()` in tests and the Alembic migration
in real deployments (the migration is still hand-written to match the model, exactly like
`0001`/`0002` already do — this repo does not autogenerate migrations from models, it writes them
by hand and keeps them in sync manually).

A materialized view would also need `REFRESH MATERIALIZED VIEW CONCURRENTLY`, which requires the
view to already be populated and to carry a plain (non-partial, non-expression) unique index
[CITED: postgresql.org/docs/current/sql-refreshmaterializedview.html] — extra machinery for no
benefit here, since the population logic already has to be hand-written application code either
way (to guarantee D-02 byte-for-byte parity via the reused composition helpers), not a `SELECT`
Postgres could execute unassisted.

### 4. Parity harness (open question #4)

Because the cache-population code is designed (per finding #2 above) to reuse `rank_section`'s own
private per-section composition helpers (`_latest_instructor_state`, `_modality_for`,
`_gened_attributes_for`, `_historical_summary`, `_signals_for`, `_signal_provenance`) and only
change *how* `analytics_stats` is obtained (pre-fetched per-course batch dict instead of a
redundant per-CRN call), byte-for-byte parity is structural, not incidental — the same Python
functions produce the same values from the same DB rows. The automated parity test should still
assert this empirically rather than trust the design: for a seeded set of sections spanning every
`score_source`/`confidence_label`/`prior_level` value and at least one section with no historical
analytics and one with no instructor observations (the "unavailable" provenance branches), assert
`rank_section(session, term=term, crn=crn)` (on-demand) equals the row constructed by joining
`section_rankings` + a live seat lookup, **field-by-field for every non-seat field**, and construct
this comparison via each Pydantic model's own equality (`SectionRanking.model_dump()` diffed
key-by-key, or the frozen dataclasses' `==`) rather than a manual field list, so a future field
addition to `SectionRanking` fails the test loudly instead of silently skipping the new field. Seat
fields must be compared separately with a controlled `as_of=` timestamp on both sides (see
Validation Architecture) since they are not expected to be byte-identical.

### 5. CHM 2045 / 2045L suffix mechanics (D-10)

Confirmed directly: `build_form_data()` (`src/easy_a/schedule/client.py:65-91`) sends
`"P_NUM": (query.course or "").strip().upper()` (line 77) to USF's staff schedule search
(`https://usfweb.usf.edu/DSS/StaffScheduleSearch/StaffSearch/Results`). `phase1_report.md` records
the observed effect: a `P_NUM=2045` search "returned **5 CHM 2045 + 40 CHM 2045L sections**"
(`phase1_report.md:52`) — i.e. USF's search treats the course-number parameter as a prefix/substring
match, not an exact match. `refresh_targets()`'s existing guard
(`src/easy_a/refresh/coverage.py:143-149`):

```python
if any(
    (r.subject, r.course_number) != (target.subject, target.number)
    or r.campus.strip() != "Tampa"
    or (crn is not None and r.crn != crn)
    for r in rows
):
    raise ValueError("Schedule response exceeded the requested Tampa/course/CRN scope.")
```

combines three independent checks (course-number exactness, Tampa-only, CRN-exactness) into one
`any(...)` that aborts the **entire** batch — including the 5 correct `CHM 2045` rows — the moment
any `CHM 2045L` row appears. STATE.md confirms this is what happened: "USF's CHM 2045 query also
returns CHM 2045L, which the exact-course guard correctly rejects" (`STATE.md:35-36`) and the pilot
worked around it by substituting a different course rather than fixing the mismatch. **33 base
courses in the full catalog have suffix variants** whose query behavior is unverified except CHM
2045 (`STATE.md:37`, `phase1_report.md:54`) — this is not a one-off, it blocks a meaningful fraction
of a full-scale run.

**The fix does not weaken the guard — it separates concerns.** Filter `rows` down to only the exact
`(subject, course_number) == (target.subject, target.number)` matches *before* evaluating the
Tampa-campus and CRN checks; keep those two checks exactly as strict as today against the filtered
set (still raising `ValueError` and rolling back if a non-Tampa or wrong-CRN row is found *among the
exact-course-number matches*). Suffix-variant rows (e.g. `CHM 2045L` when the target is `CHM 2045`)
are silently excluded from ingestion for the `CHM 2045` target — exactly as they should be, since
`CHM 2045L` is presumably itself a separately configurable target if/when it's wanted. This is a
pure pre-filter inserted before the existing `any(...)` check; the check's semantics for what it
does examine are unchanged.

### 6. Seeding a larger dataset for repeatable p95 measurement (open question #6)

The existing coverage/pilot tooling (`config/course_targets.toml`, `refresh_targets()`,
`refresh_course_coverage.py`) only exercises real USF network calls, which is inappropriate for a
repeatable, offline, CI-safe performance test (D-06/acceptance criterion 2 wants a "larger seeded
set... in a test if needed," not a live scrape). The existing `refresh_schedule` code path already
supports `SourceMode.file` (`src/easy_a/refresh/models.py`, `_refresh_schedule` in `service.py:151-173`)
for feeding pre-captured HTML instead of live network calls — this is the seam to reuse: generate
synthetic schedule/catalog HTML fixtures (or, more directly, synthetic ORM rows via
`session.add_all(...)`, matching the existing test convention already used in
`tests/refresh/test_postgres_coverage.py` and `tests/api/test_rankings_api.py`) for ~3,782
sections spanning realistic subject/course/instructor/grade-history diversity, seeded once per test
run against the real PostgreSQL integration path (`EASY_A_TEST_POSTGRES_URL`), and measure the
rewritten `/api/v1/rankings/search` endpoint's wall-clock latency over N representative queries.
Synthetic seed data must still respect D-04 (no fabricated *production* claims) — this is
explicitly a test fixture, not data inserted into the real coverage database, and must be labeled
as such in the performance report (dataset size + "synthetic test fixture over Supabase" as the
environment, distinct from the real 132/77-section pilot numbers already recorded in STATE.md).

### Pattern 1: Batch-by-course precompute (fixes the hidden quadratic cost)

**What:** Group the term's candidate sections by `(subject, course_number)` and call
`get_current_section_historical_analytics()` once per course group, exactly as
`quality/checks.py:_check_analytics` already does, instead of once per CRN.

**When to use:** Any time you need scores for more than one section — this is precisely what the
refresh-time population job does for the whole term.

**Example (pattern, following the verified existing code):**
```python
# Source: existing pattern read from src/easy_a/quality/checks.py:417-433 (_check_analytics)
```

### Pattern 2: Live seat join with the existing three-tier fallback preserved

### Anti-Patterns to Avoid

- **Calling `rank_section()` in a per-CRN loop inside the refresh job.** This "fixes" the phase's
  headline symptom (moves cost off the request path) but keeps the O(sections-in-course²)
  recomputation intact underneath, and refresh already runs against the same remote Supabase
  database — it would still take hours at ~3,782 sections. Batch by course (Pattern 1) instead.
- **Caching `SeatInfo`'s `freshness`/`age_seconds`/`observed_at`.** These are computed from
  `datetime.now(UTC)` at call time (`schedule/freshness.py:40`); caching them bakes in the
  cache-population instant as "now" forever, silently breaking the freshness UI/filter the moment
  time passes.
- **Relying on database-default `NULL` ordering for `seats_desc`.** SQLite defaults `NULL` first;
  PostgreSQL defaults differ by `ASC`/`DESC` — the existing Python code already normalizes `None`
  seats to `-1` before sorting (`_ranking_sort_key`, `api/routes/rankings.py:158`); the SQL
  replacement must use an explicit `COALESCE(seats_remaining, -1)` (or equivalent) rather than
  trust either engine's default, or SQLite unit tests and Postgres integration tests will silently
  disagree on ordering.

## Common Pitfalls

### Pitfall 1: Naming the new ORM class `SectionRanking` collides with the existing Pydantic model

**What goes wrong:** `src/easy_a/api/routes/rankings.py:12` already does
`from easy_a.rankings import RankingResolutionError, SectionRanking` (the Pydantic *response*
model, `src/easy_a/rankings/models.py:86`). Naming the new SQLAlchemy ORM class `SectionRanking` in
the same or an adjacent module creates either an import collision or a confusing situation where
two unrelated classes share a name across the codebase.
**Why it happens:** "Cache the section ranking" naturally suggests reusing the existing name.
**How to avoid:** Use a distinct class name for the ORM model (e.g. `SectionRankingCache` or
`CachedSectionRanking`); the database table itself can still be named `section_rankings` per D-01's
working name — table name and Python class name are independent.
**Warning signs:** `ImportError`/shadowing, or `mypy --strict` (already a required quality gate)
flagging incompatible redefinition.

### Pitfall 2: `refresh/cleanup.py`'s explicit-delete pattern will orphan or block on `section_rankings`

**What goes wrong:** `clean_other_campus_sections()` (`src/easy_a/refresh/cleanup.py:335-453`)
explicitly deletes `SeatSnapshot`, `SectionInstructor`, and `Syllabus` rows by captured ID **before**
deleting the `Section` rows themselves (`cleanup.py:407-411`), then runs `_verify_identities()`
(`cleanup.py:515-554`) to assert every dependent table's ID set changed by exactly the expected
amount. If `section_rankings` has an FK to `sections.id` with no `ondelete` behavior configured, a
future non-Tampa cleanup run (the same tool that already removed 47 sections per STATE.md) will hit
a foreign-key violation on the `Section` delete and roll back entirely; if the FK is nullable/absent,
it will instead leave stale, since-deleted-section cache rows behind, silently reintroducing a
version of the exact contamination problem PR #18 fixed.
**Why it happens:** The new table's relationship to `cleanup.py`'s existing, carefully audited
dependent-table pattern isn't obvious unless `cleanup.py` is actually read (as it was in this
research session).
**How to avoid:** Give `section_rankings.section_id` `ForeignKey("sections.id", ondelete="CASCADE")`
(matching `SeatSnapshot`/`SectionInstructor` at `models/sections.py:58,74`) **and** extend
`cleanup.py`'s explicit `_delete_ids(...)` sequence and `_identity_snapshot()`/`_verify_identities()`
sets to include `section_rankings` rows, so a stale-cache regression would fail the same identity
check that already guards the other three dependent tables — do not rely on the DB-level cascade
alone, since `cleanup.py` deliberately does its own explicit, verified deletes for exactly this kind
of dependent-data safety.
**Warning signs:** A cleanup dry run reporting nonzero `section_rankings` rows tied to a to-be-removed
section, or (if unguarded) a foreign-key violation on the next cleanup run after this phase ships.

### Pitfall 3: The quadratic-per-course cost hides inside `rank_course_sections` too, not just `_rank_candidate_sections`

**What goes wrong:** `rank_course_sections()` (`src/easy_a/rankings/service.py:101-130`), which
backs `GET /api/v1/rankings/course`, loops `rank_section()` per CRN **within a single course** —
so for a 41-section course like ENC 1101, it recomputes the full 41-section course-level grade
aggregate 41 times over. This endpoint is out of the phase's explicit scope (CONTEXT.md only names
`search_rankings`), but a plan that also happens to route course-detail lookups through the new
cache table (a reasonable, in-scope optimization since D-06 only mandates the *search* path) should
not assume this endpoint is already fine — it has the identical structural defect, just bounded to
one course instead of the whole term.
**Why it happens:** Both endpoints share the same `rank_section()` building block, which was
designed for single-CRN lookups (`GET /api/v1/rankings/section`), not batch use.
**How to avoid:** If the plan chooses to also serve `GET /api/v1/rankings/course` from
`section_rankings`, do so — no behavior change needed since that endpoint's contract isn't
constrained by D-03 either way, and it removes an equivalent (if smaller-scale) risk. If left alone,
note it explicitly as an accepted, unchanged, out-of-scope inefficiency rather than an oversight.
**Warning signs:** Course-detail page load times scaling with section count per course during any
later full-scale (~3,782-section) testing.

### Pitfall 4: Total-count query must reuse the exact same filter predicates as the item query

**What goes wrong:** `search_rankings()` today computes `total = len(rankings)` from the *same*
Python list it just filtered/sorted, so total and items can never disagree. A SQL rewrite that
computes `COUNT(*)` with a subtly different WHERE clause (e.g. forgetting the live seat join for
`seats_open`, or applying `min_easiness`/`confidence` only to the paginated query) will produce a
`total` that doesn't match the number of `items` a client would see across all pages — a silent
contract regression not caught by comparing a single page's `items` in a parity test.
**Why it happens:** It's easy to write the `COUNT` query as a copy-paste-and-forget rather than a
single shared query-builder function with `LIMIT`/`OFFSET` applied only for the `items` variant.
**How to avoid:** Build one SQLAlchemy `Select` with every filter (including the live seat join)
applied, then derive both the `items` query (`.order_by(...).limit(...).offset(...)`) and the
`total` query (`select(func.count()).select_from(<same filtered subquery>)`) from that one shared
statement object, so a filter can never be added to one and forgotten in the other.
**Warning signs:** A parity/acceptance test that only checks page-1 `items` will not catch this —
explicitly test `total` against an independent `COUNT` and test that summing `items` across all
pages (`offset=0,50,100,...`) equals `total` with no duplicates or gaps.

### Pitfall 5: `EASY_A_TEST_POSTGRES_URL`-gated tests are easy to leave broken without noticing

**What goes wrong:** This repo's default `pytest` run (192 passed/1 skipped per REQUIREMENTS.md) does
not exercise PostgreSQL at all; a migration or a Postgres-specific SQL construct (e.g. a window
function or `COALESCE` clause with dialect-specific syntax) that works on SQLite in the default
suite can still be broken against real Postgres and ship unnoticed, exactly the historical pattern
already called out in the project's own "Current test baseline" section.
**Why it happens:** Contributors (and CI, per REQ-OPS-01 — not yet built) may only run the default
suite.
**How to avoid:** This phase's acceptance criterion 5 already requires "Full test suite green,
including the PostgreSQL integration path" — the plan must budget explicit local verification with
`EASY_A_TEST_POSTGRES_URL` set (this research session could not do so — no Postgres was reachable —
so this is a task for the execution phase, not something this research already confirmed green).
**Warning signs:** SQL that only exists in the new migration/search-query code and was never run
against `engine.dialect.name == "postgresql"` before merge.

1. **Exact schema/column list for `section_rankings`.**
   - What we know: every non-seat field of `SectionRanking` must be representable (see the model at

   - What we know: `_rank_candidate_sections` today joins `CourseAttribute` at the `Course` level
     (`api/routes/rankings.py:114-117`) — a course can have multiple GenEd attributes.
   - What's unclear: whether to keep this as a live join against `course_attributes` (which rarely
     changes) or denormalize the attribute-code set onto each `section_rankings` row.
   - Recommendation: keep it as a live join — `course_attributes` is small, keyed by course (not

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|----------------------|
| SQL injection via search filter parameters (subject/course_number/gened_code/delivery_method/sort) | Tampering | Continue using SQLAlchemy Core's parameterized `select()`/`where()`/`order_by()` construction exclusively (as `_rank_candidate_sections` already does) for the new SQL-side query builder; never interpolate query-string values into raw SQL text |
| Denial of service via unbounded `limit`/`offset` or a pathological filter combination against the cache table | Denial of Service | The existing `Query(ge=1, le=200)` bound on `limit` (`api/routes/rankings.py:60`) is unchanged by D-03 and remains the primary control; ensure the new SQL query has supporting indexes (see Discretion note on indexing) so even a worst-case filter combination resolves via an index rather than a full-table scan at ~3,782 rows |
| A refresh-time population bug silently writing incorrect/stale scores that the search endpint then serves as if authoritative | Tampering / Information Disclosure of a subtler kind (serving wrong-but-plausible data) | The byte-for-byte parity test (D-02, Validation Architecture above) is the primary control — it is a correctness/honesty control specific to this project's "no fabricated values" core value (D-04), not just a generic security concern |
